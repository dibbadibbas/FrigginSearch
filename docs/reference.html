01 What was built

A complete local archive. Every weekly page the site has ever published was crawled once, parsed into a pages → shows → segments model, and indexed with SQLite FTS5. The crawl finished with no fetch failures and no parse errors.

The collapse in prose through the 2020s is the source, not the scraper: the site's author stopped writing detailed recaps around September 2023. Everything after that is segment titles and air times.

Stored on disk: 358 MB database, 226 MB HTML cache, 203.6M characters of prose (~50.9M tokens). 19 tests, all passing.

02 What the site actually is

None of this is documented anywhere — it was established by crawling and reading markup. It is recorded because the parser depends on all of it.

Hard-won rule

Weekly URLs are always read from the index pages, never constructed. Weeks don't align to fixed dates and early filenames are irregular — news96_97/dec-97.htm, news86/mastertape86.htm, news99/12-6-99.htm. Guessing URLs was the single biggest source of wasted effort during exploration; most apparent 404s were invented filenames.

Three page formats

Which format you get varies week to week, not by era, so it is detected per page rather than switched on the year.

Era quirks the parser absorbs

  • Banner colour changed — #ff0000 in the 1990s, #006699 later. Colour is deliberately not part of the match.
  • Comma placement varies — -- Monday, June 1, 2020 -- against -- Friday January 9, 1998 --.
  • 1998 weeks run backwards — Friday first, Monday last.
  • 1996–97 pages hold a whole month, not a week. December 1997 yields 24 shows.
  • Not every banner is a day. Wrap Up Show and various promo blocks use identical markup; undated banners fold into the day above rather than becoming dateless shows.
  • Replay banners are real but out of range — a 1998 page can legitimately contain a February 2007 section, and mastertape86.htm is dated 2007 because it documents a replay of 1986 material. Kept as-is.
  • The table of contents exists in both eras, which is where recap segments get their air times.

Transport quirks

  • No robots.txt — the URL 404s. No stated crawl rules; rate-limited to 1 req/sec regardless.
  • HTTP 406 on short User-Agent strings. "Mozilla/5.0" alone is rejected; a full browser UA works.
  • Encoding is cp1252, declared nowhere. UTF-8 decoding corrupts punctuation.
  • No ETag. If-None-Match returns a full 200. But Last-Modified is sent and If-Modified-Since returns a 0-byte 304 — this is what makes monthly updates cheap.
  • Pages are edited after publication, which is why updates revalidate rather than only hunting for new URLs.

The decision that mattered

Scraping and parsing are strictly separate. scrape writes raw HTML to data/cache/; parse only ever reads from there and never touches the network.

This paid for itself repeatedly. The parser was rewritten three times during the build — for Wrap Up Show merging, for the 1996 flat format, and for a schema change — and each full re-parse of all 1,530 pages took about two minutes and zero requests.

Idempotency. db.store_page() replaces a page's rows inside one transaction, so re-parsing never duplicates. Existing summaries are carried across by content_sha256 of title and body — improving the parser doesn't mean paying to regenerate the same text twice.

04 Database schema

pages       url PK, year_folder, filename, week_start, week_end, format,
            http_status, byte_size, content_sha256, etag, last_modified,
            fetched_at, parsed_at, parse_error

shows       id PK, seq, show_date, weekday, page_url FK, day_header,
            date_confidence, summary
            UNIQUE(page_url, seq)

segments    id PK, show_id FK, ordinal, title, air_time, anchor,
            body_text, body_chars, source_url, content_sha256, scraped_at,
            summary, summary_model, summary_effort, summarized_at, batch_id
            UNIQUE(show_id, ordinal)

segments_fts     FTS5(title, body_text, summary)
                 external content, porter unicode61, trigger-synced

summary_batches  batch_id PK, model, effort, request_count, status,
                 created_at, retrieved_at
  • shows is keyed on (page_url, seq), not on header text — the original key collided on 5 pages that repeat a banner within one page.
  • date_confidence is exact (from a banner), inferred (from a segment's own date or the week range), or unknown.
  • body_text is NULL for listing segments — there is no prose to store.
  • FTS5 stays in sync through AFTER INSERT/UPDATE/DELETE triggers, verified in tests.

Global flags: --db PATH, --rate SECONDS. Filters on scrape and parse: --since YYYY, --until YYYY, --limit N. Use parse --reparse to reprocess everything, scrape --refresh to re-download.

First-time build

markscraper discover && markscraper scrape && markscraper parse && markscraper stats

The crawl takes about 25 minutes at 1 req/sec; the parse about two minutes.

06 The monthly update

markscraper update                 # the routine monthly run
markscraper update --months 6      # look further back
markscraper update --all           # revalidate all 1,530 pages
markscraper update --summarize     # also summarise anything new
Why it isn't just "fetch new weeks"

The site edits pages after publishing. A week goes up with "Segment List Coming Later This Friggin Week" and is completed days later — 32 pages currently carry such a placeholder. Looking only for new URLs would silently miss all of that content.

Each run re-checks three sets:

  1. New weeks — both index pages re-read for unseen URLs.
  2. Recent weeks — any page with a week_start inside --months (default 3).
  3. Placeholder pages — any page still carrying a "coming later" segment, regardless of age.

Every candidate is revalidated with If-Modified-Since. Unchanged pages return a 0-byte 304; changed pages are re-downloaded, re-parsed, and their existing summaries preserved. A typical run touches ~45 pages:

$ markscraper update
0 new page(s) in the index; revalidating 45
changed 0, unchanged 45

Because the server sends no ETag, the first update after a database rebuild downloads its candidates in full to compare hashes, then stores Last-Modified so later runs get true 304s.

Automating it

# crontab -e — 06:00 on the 1st of each month
0 6 1 * * .venv/bin/python -m markscraper.cli update >> /tmp/markscraper-update.log 2>&1

07 Summarisation

A deliberately separate phase, so the archive exists first and the spend is a later decision.

markscraper summarize --dry-run                  # projection from real data
markscraper summarize --limit 5 --sync           # spot-check quality
markscraper summarize --model claude-haiku-4-5   # batch backfill
markscraper summarize --resume                   # collect finished batches
  • Batch by default, at half price. Requests are chunked (default 5,000) and each segment is stamped with its batch_id before submission, so an interrupted run is recovered with --resume rather than re-submitted. Results are keyed by custom_id, never by position.
  • --dry-run samples 25 real segments through count_tokens and extrapolates, rather than guessing.
  • --effort defaults to low, which suits extractive condensation; it is omitted automatically for models that reject it.

Backfill scale is 52,692 prose segments, ~50.9M input tokens. Batch-priced estimates:

08 Known limitations

  • 15 undated shows (0.2%) — mostly promo blocks appearing before any dated banner, plus a few 1996 segments whose date couldn't be pinned. Their segments are stored; only show_date is missing.
  • A few 1996 edge cases — aug-96.htm collapses to a single date, mar-96.htm holds one stray out-of-range date. Content is captured either way.
  • Out-of-range replay dates are intentional, not bugs.
  • Post-2023 has no prose, so there's nothing there for the summariser. That's a property of the source.
  • The etag column is vestigial — the server never sends one. Kept so the schema needn't change if that ever starts.
  • No incremental FTS rebuild. If the index is ever suspected of drift, parse --reparse rebuilds everything.

09 Environment

Python 3.14 on Ubuntu 26.04, SQLite 3.46.1 with FTS5. This machine had no pip and no ensurepip, so python3 -m venv produced a venv with no pip inside it. Resolved by bootstrapping:

python3 -m venv .venv
curl -sS https://bootstrap.pypa.io/get-pip.py | .venv/bin/python
.venv/bin/pip install -r requirements.txt

Dependencies: anthropic, requests, beautifulsoup4, lxml. The lxml parser matters — the markup is malformed enough that strict parsers drift.
